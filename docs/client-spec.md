# Client Specification

Agent (`Client` project) that runs on each monitored machine. Routes and payloads: `api-contract.md`. Detailed pseudocode: `client-pseudocode.md`.

## Hosting (decided by Sam, 2026-11-12)

The agent runs as a **Windows Service**. It is built in two phases:

1. **Phase 1: run from the IDE.** A console app started from VS Code (`dotnet run` / F5) on a Windows test client machine, against a test server. Everything in this spec works in this mode.
2. **Phase 2: the executable.** A published `.exe` installed as a Windows Service (`Microsoft.Extensions.Hosting.WindowsServices`, added through a team PR), starting with the machine and running as LocalSystem so it can read most files. The same scan, enroll and upload code runs in both phases; only the host changes.

**Windows only** (decided by Sam, 2026-11-12). Linux clients are not planned.

## Config file

JSON, path given as the first argument (default `client-config.json`). Normally **generated by the server** with **Deploy new agent** in the portal (`api-contract.md`, Admin API) and copied to the machine. Commit only a sample with fake values (`Client/client-config.example.json`).

```json
{
  "clientId": "ws-acct-01",
  "scanIntervalMinutes": 360,
  "directories": [ "C:\\FileGuard-Watch\\Finance", "C:\\FileGuard-Watch\\HR" ],
  "outputDir": "C:\\FIM\\scans",
  "logPath": "C:\\FIM\\client.log",
  "api": {
    "baseUrl": "https://fileguard.example.edu",
    "enrollmentToken": "fge_9f2c4a7b1e0d3c55_5d1e...c09a",
    "credentialPath": "C:\\FIM\\agent.key",
    "serverKeySha256": "7d1f04c3...e8a2c2a9"
  }
}
```

| Field | Required | Rules |
|---|---|---|
| `clientId` | yes | Assigned by the server. Matches `^[A-Za-z0-9._-]{1,64}$`. Used only for local file names and logs; never written to the DB or sent (the API key identifies the client). |
| `scanIntervalMinutes` | yes | Number > 0; fractions allowed (0.5 = every 30 seconds). Minutes, so short demo intervals are easy to set (decided by Sam, 2026-10-28). |
| `directories` | yes | At least one. Normalized and de-duplicated on load. A generated config may arrive with an empty list; the client then exits with "add at least one folder to `directories`". |
| `outputDir`, `logPath` | yes | Where snapshots and logs go. Keep them outside the scanned folders. |
| `api.baseUrl` | yes | Must start with `https://`. |
| `api.enrollmentToken` | until enrolled | One-time token from the server. Ignored once a key is stored at `credentialPath`. It is single-use and expires, so leaving it in the file is harmless. |
| `api.credentialPath` | yes | Where the client stores its API key after enrolling. |
| `api.serverKeySha256` | no | SHA-256 of the server certificate's public key (lowercase hex), filled in by the server. If set, the client accepts the server only when its certificate carries that key, whatever the certificate's name or issuer (this is how the self-signed server certificate is trusted, and why reissuing it with the same key needs no client change). If not set, normal certificate validation applies. |

No long-lived secret is ever written in the config file.

## Enrollment and the API key

The client has no API key until it enrolls (decided by Sam, 2026-11-11):

1. Before each upload, if there is no key at `credentialPath`, call `POST /api/v1/agent/enroll` with `enrollmentToken`, hostname, OS and client version.
2. On `200`, store the returned API key at `credentialPath`, encrypted with DPAPI (`ProtectedData`, `LocalMachine` scope), in a file readable only by SYSTEM and Administrators.
3. On `401 enrollment_invalid`, log "enrollment token rejected; deploy a new config" and skip the upload. Network errors and 5xx: try again before the next upload.
4. Scanning never waits for enrollment: scans and retention run on schedule either way.
5. If a later upload gets `401 unauthorized` (key revoked or replaced), log it and keep the key file; an admin re-deploys the config to recover.

## Schedule

- Run one scan at startup, then one every `scanIntervalMinutes`, **measured from the start of each scan** so runs don't drift.
- If a scan takes longer than the interval, the next one starts right away.
- A failed run is logged and never stops the schedule.

## Scan behavior

1. Create a new SQLite file per scan: `<outputDir>/scan_<clientId>_<unixStart>.db`, table `Data` (see `data-model.md`). Insert all rows in one transaction.
2. For each configured root:
   - Missing root: record a `DIR_NOT_FOUND` row for it and continue.
   - Walk it recursively **by hand** (a stack of folders), not `SearchOption.AllDirectories`, which aborts on the first access-denied folder.
   - Don't follow symlinks or junctions (reparse points).
3. For each file: normalize the path, skip it if already seen (overlapping roots), then hash it with streamed SHA-256 (`FileShare.ReadWrite`, 1 MB buffer, async). Size in KiB is taken from the bytes actually hashed.
4. **Failures, first try:** a file that can't be hashed goes on a retry list; a folder that can't be listed goes on a failed-folder list. Log it and keep going. One bad file or folder never stops a scan.
5. **Retry once after the full scan:**
   - Re-walk each failed folder. Files found now are hashed normally. A folder that fails again is recorded with `DIR_UNREADABLE`, `fileSize` NULL.
   - Re-try each failed file. If it fails again, record it with its error code; `fileSize` is filled if the file system still reports it, otherwise NULL.
6. Exception to error code mapping:
   - `UnauthorizedAccessException` → `PERMISSION_DENIED`
   - `FileNotFoundException` / `DirectoryNotFoundException` → `NOT_FOUND`
   - `IOException` with HResult low word 32 or 33 (sharing/lock violation) → `LOCKED`
   - Any other `IOException` → `UNREADABLE`
7. **Count `foldersScanned`:** every folder listed successfully (roots and subfolders, each once, including folders that succeed on the retry pass).
8. Commit, close, record `scanFinishedAt` (Unix seconds), log counts (hashed, errors, folders). If the scan fails before the commit, delete its incomplete DB file so it is never uploaded.

## Upload

`POST /api/v1/scans` (`api-contract.md`), right after each successful scan:

- `Authorization: Bearer <apiKey>`; HTTPS only; server public key pinned when `serverKeySha256` is set.
- Multipart with two parts: `metadata` (JSON) and `scanDb` (the snapshot file).
- `metadata` carries only what the server can't work out from the snapshot (decided by Sam, 2026-11-11):

```json
{
  "schemaVersion": 1,
  "scanStartedAt": 1793222289,
  "scanFinishedAt": 1793222361,
  "foldersScanned": 3,
  "agent": {
    "clientVersion": "1.0.0",
    "hostname": "WS-ACCT-01",
    "os": "Microsoft Windows 10.0.26200",
    "scanIntervalMinutes": 360,
    "directories": [ "c:/fileguard-watch/finance", "c:/fileguard-watch/hr" ]
  }
}
```

  `hostname` = `Environment.MachineName`, `os` = `RuntimeInformation.OSDescription`, `clientVersion` = the assembly's informational version, `directories` = the normalized roots from the config.
- **No client ID field**, and no file counts or new/changed/deleted totals: the server counts files from the snapshot and works out changes in its merge.
- **Retry policy:** at most 3 attempts, waiting 5 s then 30 s (no wait after the last); 10-minute timeout per attempt. Retry only network errors, timeouts and 5xx. Never retry a 4xx (400, 401, 409, 413).
- **409 `scan_out_of_order`** means the server already merged a newer scan, which almost always means this machine's clock went backwards. Log it as an error that says so ("server has a newer scan; check this machine's clock"). The server also logs it and shows an alert in the portal.
- If the upload ultimately fails, **don't re-send it later**: the next scan uploads newer data, and the server rejects scans older than one it has already merged. The snapshot stays on disk until retention removes it.

## Local snapshot retention

The client stays lightweight; the server does long-term storage (decided by Sam, 2026-10-28).

- After each run (scan, then upload), delete older snapshots in `outputDir`, keeping only the **2 newest** `scan_<clientId>_*.db` files: the current one and the one before it.
- Order snapshots by the `<unixStart>` in the file name. Only touch files matching this client's pattern.
- A failed delete is logged and never stops the schedule.

## Not the client's job

- Diffing against earlier scans (the server does all of it).
- Remembering previous scans, or keeping snapshots long term (see retention above).
- Choosing its own client ID (the server assigns it).
